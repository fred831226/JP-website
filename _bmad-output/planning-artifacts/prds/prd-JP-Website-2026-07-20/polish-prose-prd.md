# JP-Website PRD Prose Review

| Original Text | Revised Text | Changes |
|---------------|--------------|---------|
| **Thesis：** JP-Website 是 JP PUMP 的公開專業線上型錄與數位信任入口…… | **核心主張：** JP-Website 是 JP PUMP 的公開專業線上型錄與數位信任入口…… | 將非必要英文標籤改為繁中，避免非技術決策者需要推測 `Thesis` 的用途（§0）。 |
| 傑平品牌與經確認的國外品牌首發內容；電話與 Email 聯絡入口及聯絡意圖量測。 | 傑平品牌與經確認的國外品牌首發內容。網站亦提供電話與 Email 聯絡入口及聯絡意圖量測。 | 原句以分號連接「首發內容」與「聯絡量測」兩個不同範疇；拆成兩句以釐清並列關係（§0.1）。 |
| 最小化合格詢問紀錄／最小化詢問紀錄 | 最小必要的合格詢問紀錄／最小必要的詢問紀錄 | 「最小化」可能被理解為減少詢問數量；改為「最小必要」以表達只記錄必要欄位（§0.1、§3.6）。 |
| ### 0.3 發布阻塞與未決技術；**未決技術：** 後端、CMS、主機、網域、媒體儲存及分析同意方式…… | ### 0.3 發布阻塞與待決事項；**待決事項：** 後端、CMS、主機、網域、媒體儲存及分析同意方式…… | 網域與分析同意方式不全是技術選擇；改用涵蓋範圍較準確的名稱，不改變待決內容。 |
| 海外陌生開發在 V1 主要獲得公司存在與能力的基本驗證；完整英文產品探索延後處理。 | 海外陌生開發對象在 V1 主要能驗證公司的存在與能力；完整的英文產品探索延後處理。 | 「陌生開發」是活動而非人；補上「對象」，並把動作主體與受詞說清楚（§1.3）。 |
| 在產品與信任資訊建立足夠信心後，讓訪客能從當下情境直接採取電話或 Email 聯絡。 | 在產品資訊與信任證據足以建立信心後，讓訪客能從當下情境直接以電話或 Email 聯絡。 | 原句會被讀成「資訊建立信心」且「採取聯絡」搭配不自然；調整主從關係與動詞（產品目標 4）。 |
| 並由 FR-14 與 FR-24 確保產品資料可追溯及完成技術覆核。 | 並由 FR-14 與 FR-24 確保產品資料可追溯，且已完成技術覆核。 | 修正不對稱並列，釐清「可追溯」與「完成覆核」是兩項條件（§3.4）。 |
| 並上傳圖片及完成來源與使用權資訊。 | 並上傳圖片，填妥來源與使用權資訊。 | 「完成資訊」搭配不自然；改為明確的填寫動作（UJ-4）。 |
| 他取得 JP PUMP 技術人員的線下確認並記錄，預覽完整網站變更後發布可識別版本。 | 他取得並記錄 JP PUMP 技術人員的線下確認，預覽完整的網站變更後，再發布具版本識別的內容。 | 原句不清楚「記錄」的受詞，也可能被讀成「預覽後發布版本」缺少先後關係；補足受詞與停頓（UJ-5）。 |
| 手機與桌機均能到達相同核心內容，且目前頁面與導覽層級清楚可辨。 | 手機與桌機均能到達相同核心內容，且使用者目前所在頁面與導覽層級清楚可辨。 | 「目前頁面」可能指目前版本的頁面；補上「使用者所在」以消除歧義（FR-1）。 |
| 未通過權利、安全或敏感資訊檢查的欄位與媒體不公開。 | 未通過使用權、安全性或敏感資訊檢查的欄位與媒體不得公開。 | 將抽象的「權利、安全」改為一致的檢查項目名稱，並把發布限制寫成直接要求（FR-4）。 |
| 一次操作不重複計數。／同一次聯絡動作不重複觸發。 | 同一次使用者操作不得觸發重複計數。 | 合併兩處對同一追蹤防重要求的不同表述，釐清「觸發」的是重複計數而非聯絡動作（FR-17、FR-35）。 |
| 指定網站維護者可在正式發布前查看新增、修改、移除及受影響頁面。 | 指定網站維護者可在正式發布前查看新增、修改及移除項目，以及受影響的頁面。 | 原清單把變更類型與頁面並列，關係不清楚；補上共同受詞並分隔兩類資訊（FR-23）。 |
| 每次產品發布可識別版本，並可回復上一個可用版本。 | 每次產品發布均須具有可識別的版本，並可回復至上一個可用版本。 | 補上謂語與介系詞，使版本識別和回復要求完整且直接（FR-23）。 |
| 每筆來源資料都有已發布、待覆核、資料不足或排除結果。 | 每筆來源資料都必須有明確處理結果：已發布、待覆核、資料不足或排除。 | 原句容易把四個狀態讀成「資料內容」；先說明分類性質，再列出結果（FR-25）。 |
| 沒有英文內容時不產生空白頁或自動翻譯內容。 | 沒有英文內容時，不得產生空白英文頁或自動翻譯內容。 | 補出「空白頁」的語言範圍，並與其他驗收條件一致地使用直接要求（FR-26）。 |
| 必須交付產品更新操作文件……／產品分類或技術資料的新增……／更新回應時間屬維護合約…… | **跨項營運規則：** 必須交付產品更新操作文件……／產品分類或技術資料的新增……／更新回應時間屬維護合約…… | 三個條列緊接 FR-26，容易被誤認為多語驗收條件；加上短標籤說明其適用範圍，不改變內容（FR-26 後）。 |
| 重新命名或移動內容時，舊網址導向最相關的新網址，不任意全部導回首頁。 | 重新命名或移動內容時，舊網址須導向最相關的新網址，不得將所有舊網址一律導回首頁。 | 「不任意全部」語序含混；改成明確禁止的一致性要求（FR-28）。 |
| V1 驗收資料正確性與搜尋資格，不承諾 Google 一定顯示產品複合式搜尋結果。 | V1 僅驗收資料正確性與搜尋資格，不承諾 Google 一定顯示產品複合式搜尋結果。 | 加上「僅」以明確界定驗收承諾與非承諾之間的界線（FR-32）。 |
| 公開站主要流程符合 WCAG 2.2 AA，包括完整鍵盤操作、清楚焦點、合理標題結構、圖片替代文字、表單與錯誤文字…… | Consider: 公開站主要流程符合 WCAG 2.2 AA，包括完整鍵盤操作、清楚可見的焦點狀態、合理的標題結構、圖片替代文字、表單標籤與錯誤訊息…… | 「清楚焦點」與「表單與錯誤文字」意義不完整；建議確認原意是否分別為焦點狀態、表單標籤和錯誤訊息（NFR-3）。 |
| 帳號採最小權限、登入防暴力嘗試及安全的恢復流程。依賴套件與部署環境須接受漏洞檢查，高風險漏洞不得帶入正式發布。 | 帳號採最小權限，並具備登入防暴力破解措施及安全的帳號恢復流程。依賴套件與部署環境須進行漏洞檢查；存在高風險漏洞時，不得正式發布。 | 修正「登入防暴力嘗試」與「接受漏洞檢查」的不自然搭配，並明確連結高風險漏洞與發布限制（NFR-5）。 |
| Cookie 與非必要分析依適用同意狀態運作。 | Cookie 與非必要分析功能須依適用的同意狀態啟用。 | 補上動作與受詞，說清楚同意狀態控制的是功能啟用（NFR-6）。 |
| 正式站須監控無法存取、部署失敗、重大前端錯誤、Core Web Vitals、失效連結及索引異常。不得等客戶回報後才知道網站完全失效。 | 正式站須監控網站可用性、部署失敗、重大前端錯誤、Core Web Vitals、失效連結及索引異常，並在客戶回報前偵測到全站失效。 | 「監控無法存取」搭配不自然，後句也偏口語；改為可理解且可驗收的偵測要求（NFR-9）。 |
| 重大錯誤能阻止發布。 | 重大錯誤必須阻止發布。 | 「能」只表示能力，不表示強制門檻；改為與本文既有決策一致的直接要求（NFR-11）。 |
| 公開站應呈現完整、專業、現代、技術可信且不花俏的工業 B2B 體驗。 | 公開站應呈現資訊完整、專業、現代、技術可信且不花俏的工業 B2B 體驗。 | 補出「完整」修飾的是資訊，避免讀者把它理解為未定義的整體完整度（NFR-13）。 |
| 未核對真實產品規格的 AI 圖 | 未依真實產品規格核對的 AI 生成圖片 | 將口語縮寫改為完整名稱，並釐清核對依據（NFR-13）。 |
| 首頁影片與大量圖片過重 \| 手機跳出、Core Web Vitals 失敗 | 首頁影片與大量圖片過重 \| 手機訪客離站率上升、Core Web Vitals 未達標 | 「手機跳出」與「失敗」較口語且不精確；改為可被團隊一致理解的影響描述（§8.2 風險表）。 |
| V1 只有繁中 \| 海外陌生開發仍無法完整探索產品 \| 誠實限制主張；保留英文資料模型與獨立網址 | V1 只有繁中 \| 海外陌生開發對象仍無法完整探索產品 \| 明確說明語言限制；保留英文資料模型與獨立網址 | 補出「陌生開發對象」，並將不自然的「誠實限制主張」改為具體的溝通行動（§8.2 風險表）。 |
| 正式受控分類與最低規格欄位 | 正式受控分類與最低必要規格欄位 | 「最低規格」可能被理解為數值下限；加上「必要」以表達待確認的是最少必填欄位（§9 未決事項 3）。 |
